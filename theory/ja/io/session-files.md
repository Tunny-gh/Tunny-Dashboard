# セッションファイル

## 概要

セッションファイル（素の JSON、`*-session.json` として保存）は、データそのものではなく**データをどう見ているか**を保存する。永続化されるのは次の 3 層である。

- **キャンバスレイアウト** — 配置されているウィジェット、位置・サイズ、重なり順、パン/ズーム、パネル状態
- **ウィジェットごとの設定** — 配置された各ウィジェットのユーザー調整可能な全設定（軸・列の選択、クラスタ数、MCDM 重み、ヒストグラムのビン規則、正規化・対数スケールのトグル、実行可能フィルタ、3D カメラ姿勢など）。同じウィジェットを複数配置した場合も各アイテムが独立した設定を保持する
- **グローバル表示設定** — カラーマップ、フィルタ範囲、ピン留めトライアル、HV 参照点、収束指標、ヘルプ言語

最適化データ（journal / SQLite / CSV）およびそこから導出される計算結果は、意図的に**保存しない**。

---

## 状態分離の原則

アプリケーションの状態は 3 つのカテゴリに分けられ、セッションの境界はそこから直接導かれる。

| カテゴリ | 例 | セッションに含む? |
| -------- | -- | ----------------- |
| データ | トライアル、目的関数値、Study メタデータ | 含まない — ストレージファイルの持ち物 |
| 導出状態 | Pareto ランク、クラスタ割当、学習済みサロゲート、MCDM スコア、キャッシュ | 含まない — (データ, 設定) の純関数 |
| ビュー状態 | レイアウト、ウィジェット設定、カラーマップ、フィルタ | **含む** |

導出状態を除外するのは、それが完全に再現可能だからである。セッション復元後は、各ウィジェットの通常のポーリング経路が「現在のデータ + 復元された設定」から結果を再計算する。導出状態を保存すると、データが変わった場合に古い結果を表示するリスクが生じ、モデル重みやキャッシュでファイルが肥大化するだけである。

データを保存しないため、セッションは**別のデータセット**に対しても適用できる。別の Study を開けば、同じダッシュボード構成がそのまま再利用される。列参照の不整合はアプリ内で Study を切り替えたときと同じ挙動で処理される — 名前ベースの参照（軸・列の選択）は存在しない名前ならデフォルト列にフォールバックし、インデックスベースの参照は有効範囲に収められる。

## フォーマットとスキーマ進化

ファイルは単一の JSON ドキュメントである。

```json
{ "version": 1, "layout": { ... }, "widgets": { "<item-id>": { ... } }, "view": { ... } }
```

互換性は *tolerant reader*（寛容な読み手）パターンに従う。

- **未知のフィールドは無視**して読み込むため、新しいマイナー版が書いたファイルも開ける
- **欠落フィールドは既定値**で補うため、古い版が書いたファイルも開ける。新しく追加された設定は単に既定値から始まる
- したがって `version` 番号は**破壊的**変更（フィールドの意味や型が変わる場合）でのみ引き上げる。アプリが理解できるより新しいバージョンのファイルは、誤読せず明示的なエラーで拒否する

ランタイム専用フィールド（計算結果、キャッシュ、学習済みモデル、モーダル状態）は型レベルで除外されている。シリアライズ時にスキップ指定されているため、ファイルへ漏れることはなく、読み込み時には既定値にリセットされる。

---

## 特性

- セッション復元は最適化データへの I/O を一切発生させない。レイアウトと設定を置き換えるだけなので瞬時に完了し、データ読み込み済みの状態でも安全に適用できる
- ピン留めトライアル ID とフィルタ範囲はそのまま保存される。別のデータセットに対しては存在しないトライアルや範囲を参照し得るが、存在しない ID は各ウィジェットが無視し、存在しない列のフィルタは効果を持たない
- セッションファイルは可読な JSON なので、ダッシュボード構成を diff で比較したり、プロジェクトと一緒にバージョン管理したりできる

---

## アプリ内での利用箇所

- **Save Session / Load Session ツールバーボタン**: 現在のダッシュボードをセッション JSON ファイルへ保存、または読み込み済みデータを維持したまま復元する。
