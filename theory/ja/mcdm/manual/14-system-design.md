# 第14章 システム実装における設計ポイント

## 実装設計の全体像

MCDMをシステムに実装する場合は、評価計算ロジックだけでなく、入力データ、評価基準、重み、結果、ログ、再計算条件を一貫して管理する必要があります。

システム上の基本的な流れは次のとおりです。

```text
1. 入力データを受け取る
2. 実行可能性と候補集合を管理する
3. 評価基準と評価方向を管理する
4. 重みを設定または計算する
5. 正規化とMCDM計算を行う
6. スコアとランキングを返す
7. 計算条件と結果を記録する
```

実装では、同じ入力条件から同じ結果を再現できること、エラー時に原因を特定できること、結果の前提をユーザーに説明できることが重要です。

## 入力データ構造

MCDMの入力データは、代替案、評価基準、評価値、評価方向、重みから構成されます。

代表的な入力構造は次のとおりです。

| 要素 | 内容 |
| --- | --- |
| alternatives | 個体ID、トライアル番号、名称、メタデータ。 |
| criteria | 評価基準ID、名称、単位、評価方向。 |
| values | 代替案 × 評価基準の評価値。 |
| weights | 評価基準ごとの重み。 |
| method | 使用するMCDM手法。 |
| options | 正規化方式、VIKORのvなどの追加設定。 |
| feasibility | 制約充足、実行可能性、除外理由。 |
| candidate_set | 全個体、非劣解集合、ユーザー選択集合などの候補範囲。 |

実装上は、評価値を2次元配列として扱う場合と、行指向のレコードとして扱う場合があります。

```text
values[i][j] = 代替案 i の評価基準 j に対する評価値
```

入力検証では、代替案数、評価基準数、評価値配列のサイズが一致しているかを確認します。欠損値、NaN、無限大、重みの合計0なども明示的に扱う必要があります。

## 候補集合と選択状態の管理

多目的最適化結果を扱うシステムでは、MCDM計算に入れる候補集合を明示的に管理します。全個体を対象にするのか、パレートフロント上の個体だけを対象にするのか、ユーザーが選択した個体だけを対象にするのかで、ランキングの意味が変わるためです。

候補集合に必要な情報は次のとおりです。

| 属性 | 説明 |
| --- | --- |
| set_id | 候補集合を識別するID。 |
| source | all、pareto_front、filtered、manual_selectionなど。 |
| included_ids | 対象個体IDの一覧。 |
| excluded_ids | 除外個体IDと除外理由。 |
| constraints | 適用した制約条件。 |
| created_at | 候補集合を作成した時刻。 |

また、結果表示では、MCDMランキング上の選択状態と、最適化ビュー上の選択状態を同期できると便利です。例えば、ランキング表で上位個体を選ぶと、パレート散布図や並行座標でも同じ個体が強調表示されるようにします。

## 評価基準・重みの管理

評価基準と重みは、MCDM結果の意味を決める重要な設定です。システムでは、評価基準と重みを単なる数値配列として扱うのではなく、意味を持つ設定として管理します。

評価基準に必要な属性は次のとおりです。

| 属性 | 説明 |
| --- | --- |
| id | 評価基準を識別するID。 |
| name | 表示名。 |
| direction | benefit または cost。 |
| unit | 単位。 |
| description | 基準の説明。 |
| value_source | 評価値の取得元。 |

重みに必要な属性は次のとおりです。

| 属性 | 説明 |
| --- | --- |
| criterion_id | 対応する評価基準ID。 |
| value | 重みの値。 |
| method | 手動設定、AHP、エントロピー法など。 |
| reason | 重み設定の理由。 |

重みは、内部計算前に合計が1になるよう正規化することが多いです。ただし、ユーザーが入力した元の値も保持しておくと、設定意図を確認しやすくなります。

## 計算ロジック

計算ロジックは、入力検証、正規化、重み適用、手法別計算、ランキング生成に分けると保守しやすくなります。

```text
validate_input()
normalize_values()
apply_weights()
compute_method()
rank_results()
build_result_metadata()
```

手法別の計算は、共通インターフェースを持たせると拡張しやすくなります。

| 処理 | 共通化の観点 |
| --- | --- |
| 入力検証 | サイズ、欠損値、重み、評価方向の確認。 |
| 正規化 | Min-Max、ベクトル正規化などを切り替え可能にする。 |
| 手法計算 | TOPSIS、VIKOR、PROMETHEEなどを独立実装にする。 |
| ランキング | 昇順・降順・同点処理を手法ごとに定義する。 |
| メタデータ | 使用条件、計算時刻、警告を記録する。 |

計算ロジックでは、例外ケースを明確にします。例えば、全代替案が同じ値を持つ基準、列ノルムが0になる基準、NaNを含む代替案などです。

## 結果表示

MCDMの結果表示では、ランキングだけでなく、スコアの根拠を確認できる表示が重要です。

表示すべき情報は次のとおりです。

- 総合ランキング
- 総合スコアまたは手法固有指標
- 評価基準ごとの値
- 正規化後の値
- 重み
- スコア寄与
- 使用した手法と正規化方式
- 警告や注意事項
- 制約状態と候補集合の作成条件
- パレートフロント上での位置

ランキング表の例は次のとおりです。

| 順位 | 個体 | スコア | 主な強み | 主な弱み |
| ---: | --- | ---: | --- | --- |
| 1 | A | 0.82 | リスク、保守性 | コスト |
| 2 | B | 0.78 | 性能 | 納期 |
| 3 | C | 0.61 | コスト | 性能 |

ユーザーが結果を解釈できるように、順位の理由を評価基準ごとの内訳として表示することが望ましいです。

個体選択では、ランキング表だけでなく、可視化との連携も重要です。パレート散布図、並行座標、目的関数ごとの分布、重み感度チャートと連携することで、上位個体がどのようなトレードオフを持つかを確認できます。

## ログ・監査性

MCDMの結果は意思決定に使われるため、計算条件と結果を記録しておく必要があります。監査性を確保することで、後から「なぜこの順位になったのか」を確認できます。

記録すべきログ情報は次のとおりです。

| 情報 | 説明 |
| --- | --- |
| input_hash | 入力データの識別子。 |
| criteria_version | 評価基準定義のバージョン。 |
| weights | 使用した重み。 |
| normalization | 正規化方式。 |
| method | 使用したMCDM手法。 |
| options | 手法固有パラメータ。 |
| candidate_set | 候補集合の作成条件と対象個体ID。 |
| feasibility_filter | 制約違反・実行不能個体の除外条件。 |
| warnings | 欠損値、外れ値、ゼロ除算などの警告。 |
| result | スコア、ランキング、実行時刻。 |

ログには、計算に影響した設定を含めます。ランキングだけを保存しても、再現性は確保できません。

## 再計算・バージョン管理

MCDMの結果は、入力データや設定が変わると再計算が必要です。システムでは、どの変更で再計算が必要になるかを明確にします。

再計算が必要な変更は次のとおりです。

- 評価値が変わった
- 代替案が追加・削除された
- 候補集合や制約フィルタが変更された
- 評価基準が追加・削除・変更された
- 評価方向が変更された
- 重みが変更された
- 正規化方式が変更された
- MCDM手法または手法パラメータが変更された

一方で、表示順や色、フィルタ表示など、計算結果自体に影響しない変更では再計算が不要な場合があります。

バージョン管理では、評価基準定義、重み設定、計算結果を関連付けて保存します。これにより、過去の意思決定を再現し、後から条件変更の影響を比較できます。

MCDMのシステム実装では、計算精度だけでなく、再現性、説明可能性、変更管理を設計に含めることが重要です。
