# 第6章 個体選択のための評価基準設計

## 評価基準設計の位置づけ

評価基準は、MCDMで代替案を比較するための観点です。どの評価基準を使うかによって、ランキング結果の意味は大きく変わります。評価基準が適切でなければ、どれだけ高度なMCDM手法を使っても、意思決定に役立つ結果は得られません。

評価基準の設計では、単に測定できる項目を並べるのではなく、意思決定の目的に対して必要な観点を選び、比較可能な形に整理します。特に、評価基準の意味、測定方法、評価方向、重複の有無、データ品質を明確にすることが重要です。

評価基準を設計する際の基本的な観点は次のとおりです。

| 観点 | 確認内容 |
| --- | --- |
| 関連性 | 意思決定の目的に直接関係しているか。 |
| 測定可能性 | 数値または一貫した評価尺度で表せるか。 |
| 比較可能性 | 代替案間で同じ条件・同じ意味で比較できるか。 |
| 独立性 | 他の評価基準と意味が過度に重複していないか。 |
| 説明可能性 | なぜその基準を使うのかを説明できるか。 |

MCDMでは、評価基準が意思決定の前提そのものになります。そのため、評価計算を始める前に、各基準が何を表し、どのように測定され、値が大きいほど良いのか小さいほど良いのかを明示しておく必要があります。

## 目的関数と評価基準の対応

多目的最適化結果を扱う場合、最適化で使った目的関数をMCDMの評価基準として使うことが基本になります。ただし、目的関数をそのまま使えば十分とは限りません。最適化の目的関数は探索を誘導するための指標であり、最終的な採用判断に必要な観点をすべて含んでいるとは限らないからです。

| 最適化側の情報 | MCDMでの扱い | 例 |
| --- | --- | --- |
| 目的関数 | 評価基準として使う | 精度、コスト、処理時間 |
| 制約条件 | 事前フィルタまたは評価基準にする | 最大コスト、最小強度、許容リスク |
| 制約余裕 | 追加評価基準にする | 上限までの余裕、違反量 |
| 探索メタ情報 | 説明・追跡情報として使う | trial id、世代、パラメータ |
| 実務上の観点 | 必要に応じて追加基準にする | 安定性、再現性、実装容易性 |

目的関数を評価基準に変換するときは、各目的がベネフィット型かコスト型かを明示します。例えば、精度は大きいほど良い基準、処理時間とコストは小さいほど良い基準です。

最適化に含めていない観点を後から評価基準に追加する場合は、その基準が全個体に対して公平に取得できるかを確認します。一部の個体だけ追加評価がある場合、ランキングが偏る可能性があります。

## 定量基準と定性基準

評価基準は、大きく定量基準と定性基準に分けられます。

定量基準は、数値として直接測定できる基準です。価格、処理時間、精度、利益、消費電力、故障率などが該当します。定量基準は評価行列にそのまま入力しやすく、計算結果の再現性も高くなります。

定性基準は、直接的な数値では表しにくい基準です。操作性、保守性、導入しやすさ、サポート品質、ブランド信頼性などが該当します。定性基準をMCDMで扱う場合は、段階評価やスコアリングにより数値化する必要があります。

| 種類 | 例 | 特徴 | 注意点 |
| --- | --- | --- | --- |
| 定量基準 | 価格、処理時間、精度、利益 | 測定値をそのまま使いやすい | 単位や測定条件をそろえる必要がある |
| 定性基準 | 操作性、保守性、導入容易性 | 実務上重要な観点を反映しやすい | スコア化の基準が曖昧になりやすい |

定性基準を数値化する場合は、評価尺度を事前に定義します。例えば、保守性を5段階で評価する場合、各スコアが何を意味するのかを明確にします。

| スコア | 保守性の評価例 |
| ---: | --- |
| 5 | ドキュメントが十分で、担当者以外でも保守できる |
| 4 | 基本的なドキュメントがあり、軽微な修正は容易 |
| 3 | 保守可能だが、担当者の知識に依存する |
| 2 | 構造が複雑で、修正時の影響範囲が読みづらい |
| 1 | 保守に大きなリスクがある |

このように、定性基準を使う場合は、評価者によるばらつきを小さくするために、スコアの意味を具体化することが重要です。

## ベネフィット型・コスト型基準

評価基準には、値が大きいほど望ましい基準と、値が小さいほど望ましい基準があります。MCDMでは、この評価方向を明示しないと、正規化やスコア計算で逆の評価をしてしまう可能性があります。

値が大きいほど望ましい基準をベネフィット型基準と呼びます。性能、品質、利益、精度、可用性などが該当します。

値が小さいほど望ましい基準をコスト型基準と呼びます。価格、処理時間、リスク、損失、消費電力、エラー率などが該当します。

| 評価方向 | 意味 | 例 |
| --- | --- | --- |
| ベネフィット型 | 値が大きいほど望ましい | 性能、利益、精度、品質、可用性 |
| コスト型 | 値が小さいほど望ましい | 価格、時間、リスク、損失、消費電力 |

例えば、次のような評価基準があるとします。

| 評価基準 | 値の意味 | 評価方向 |
| --- | --- | --- |
| 価格 | 導入に必要な費用 | 小さいほど良い |
| 処理速度 | 1秒あたりの処理件数 | 大きいほど良い |
| エラー率 | 全処理に対する失敗率 | 小さいほど良い |
| サポート品質 | サポート体制の評価スコア | 大きいほど良い |

評価方向は、MCDM手法によって扱い方が異なります。TOPSISのように理想解と反理想解を使う手法では、ベネフィット型では最大値が正理想解になり、コスト型では最小値が正理想解になります。単純な加重和を使う場合は、コスト型基準を反転または変換してから統合する必要があります。

評価方向を誤ると、低コストや低リスクの代替案が不利に評価されるなど、結果が根本的に誤ります。そのため、評価基準を定義する段階で、必ず評価方向を記録します。

## 制約条件と実行可能性

個体選択では、制約条件の扱いを評価基準とは分けて考える必要があります。制約には、満たさなければ採用できないハード制約と、満たすほど望ましいソフト制約があります。

| 種類 | 説明 | 推奨される扱い |
| --- | --- | --- |
| ハード制約 | 違反すると採用不能な条件 | MCDM前に除外する |
| ソフト制約 | 余裕が大きいほど望ましい条件 | 評価基準として扱う |
| 制約違反量 | 違反の大きさを示す値 | 除外またはペナルティ基準にする |
| 制約余裕 | 上限・下限からの余裕 | 安全側の評価基準として扱う |

例えば、最大重量を超える個体が実装不能であれば、その個体はMCDMの前に除外します。一方で、重量制約を満たす個体の中で、余裕が大きいほど安全に設計できるなら、制約余裕を評価基準として追加できます。

制約違反個体をMCDMに含める場合は、ランキング上位に出たとしても採用できない可能性があります。そのため、結果表示では実行可能性を明示し、実行不能個体が誤って採用候補にならないようにします。

## 評価基準の独立性

評価基準は、できるだけ独立した意味を持つように設計します。似た意味の基準を複数入れると、同じ観点を重複して評価することになり、ランキング結果が偏る可能性があります。

例えば、次のような基準は重複している可能性があります。

| 基準1 | 基準2 | 重複の可能性 |
| --- | --- | --- |
| 処理時間 | 処理速度 | 同じ性能特性を逆方向から表している可能性がある |
| 初期費用 | 導入コスト | ほぼ同じ費用項目を表している可能性がある |
| エラー率 | 信頼性 | 信頼性をエラー率から評価している場合は重複する |
| 保守性 | 運用負荷 | 運用負荷が保守性の一部であれば重複する |

重複した評価基準を入れると、その観点の実質的な重みが大きくなります。例えば、「処理時間」と「処理速度」を別々の基準として入れ、さらに両方に重みを設定すると、性能面を二重に評価することになります。

評価基準の独立性を確認するには、次の問いが有効です。

- 2つの基準は同じ事象を別の表現で測っていないか
- 片方の基準がもう片方の基準からほぼ導けないか
- 両方を入れることで、特定の観点を過度に重視していないか
- 意思決定者に対して、それぞれの基準の違いを説明できるか
- 相関が高い場合でも、意思決定上は別の意味を持つか

完全に独立した評価基準だけを選ぶことは難しい場合があります。重要なのは、重複の有無を確認し、重複がある場合は統合する、片方を削除する、または重みで調整することです。

## 基準設定時の注意点

評価基準を設定する際は、意思決定の目的に合っているか、測定できるか、説明できるかを確認します。特に、評価基準が多すぎる場合や、抽象的すぎる場合は、計算結果の解釈が難しくなります。

よくある問題と対策は次のとおりです。

| 問題 | 例 | 対策 |
| --- | --- | --- |
| 基準が曖昧 | 「使いやすさ」「良さ」など意味が広い | 評価尺度や評価観点を具体化する |
| 基準が重複 | コストと費用を別基準にする | 統合または片方を削除する |
| 測定条件が異なる | 別期間のデータを比較する | 測定条件や集計期間をそろえる |
| 評価方向が不明 | 値が大きいほど良いか分からない | ベネフィット型・コスト型を明記する |
| 基準が多すぎる | 似た指標を多数入れる | 意思決定に効く基準に絞る |
| 主観評価が不安定 | 評価者により点数が変わる | スコアリング基準を定義する |

評価基準を確定する前に、次のチェックリストを確認します。

- 意思決定の目的に対して必要な基準か
- すべての代替案で評価値を取得できるか
- 評価値の単位や測定条件が明確か
- ベネフィット型かコスト型かが定義されているか
- 定性基準の場合、スコアの意味が定義されているか
- 他の基準と意味が過度に重複していないか
- 結果を説明するときに、その基準を使った理由を説明できるか

評価基準は、MCDMの計算結果に対する説明責任の中心になります。ランキング結果に納得感がない場合、原因は手法ではなく評価基準の設計にあることも多くあります。そのため、評価基準は一度決めて終わりではなく、結果を確認しながら必要に応じて見直す対象として扱います。

ただし、ランキング結果を見てから都合のよい基準に変更すると、意思決定の客観性が損なわれます。基準を変更する場合は、変更理由を記録し、変更前後の結果を比較できるようにしておくことが重要です。
