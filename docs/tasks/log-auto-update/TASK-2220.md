## タスク概要

TASK-2219で作成したポーリングループに、エラー連続カウント（3回で自動停止）、ファイル削除検出、60秒無変化時の最適化完了通知を追加する。これにより、異常系のエラーハンドリングとユーザへの完了通知を実現する。

## 要件との対応

- **REQ-LU-010**: 60秒間ファイルに変化がない場合、最適化完了の可能性を通知する
- **REQ-LU-101**: ファイルアクセスエラーが3回連続した場合、ポーリングを自動停止する
- **EDGE-LU-001**: 監視中のファイルが削除された場合のエラー検出
- **EDGE-LU-002**: ファイルアクセス権限エラーの連続カウント
- **EDGE-LU-003**: ファイルが一時的にアクセス不能になった場合の復旧可能性（エラー→成功でカウントリセット）

## 実装詳細

### 1. エラーカウント変数の追加 🔵

**信頼性**: 🔵 *REQ-LU-101「3回連続エラーで自動停止」より*

**実装ファイル**: `egui-app/src/io/live_update_poller.rs`

ポーリングループ内にローカル変数としてエラーカウントを追加する:

```rust
let mut error_count: u32 = 0;
```

ループ内で`fs::metadata`等のファイル操作結果に応じてカウントを増減させる。

### 2. エラー時のカウント増加と成功時のリセット 🔵

**信頼性**: 🔵 *EDGE-LU-003「エラー→成功でカウントリセット」より*

- `fs::metadata`またはファイル読み込みでエラーが発生: `error_count += 1`
- ファイル操作が成功: `error_count = 0`
- エラー発生時は`tx.send(AppMessage::LiveUpdateError)`でエラー通知も送信

### 3. 3回連続エラーでの自動停止 🔵

**信頼性**: 🔵 *REQ-LU-101「自動停止」・dataflow.md フロー4より*

```rust
if error_count >= 3 {
    let _ = tx.send(AppMessage::LiveUpdateError("連続エラーにより自動停止".into()));
    stop_signal.store(true, Ordering::Relaxed);
    break;
}
```

エラーカウントが3に達した時点で、`stop_signal`をtrueに設定しループを抜ける。エラーメッセージをUIスレッドに送信してから停止する。

### 4. 最適化完了通知の実装 🔵

**信頼性**: 🔵 *REQ-LU-010「60秒無変化で完了通知」・dataflow.md フロー4より*

- ポーリングループ内で最終ファイル変更時刻を`SystemTime`で記録
- ファイルサイズが変化した場合は最終変更時刻を現在時刻で更新
- ポーリングサイクルごとに「現在時刻 - 最終変更時刻」を計算
- 60秒経過している場合、`tx.send(AppMessage::LiveUpdateMaybeComplete)`を送信
- 完了通知後もポーリングは継続する（最適化が再開される可能性があるため）

```rust
let last_changed: SystemTime = SystemTime::now();
// ...ループ内...
if now.duration_since(last_changed).unwrap_or_default() >= Duration::from_secs(60) {
    let _ = tx.send(AppMessage::LiveUpdateMaybeComplete);
}
```

通知送信後は最終変更時刻をリセットし、重複通知を防ぐ。

### 5. panic時の安全なスレッド終了 🟡

**信頼性**: 🟡 *予期しないpanicの安全性は実行時挙動に依存するため*

ポーリングスレッド全体を`std::panic::catch_unwind`でラップする:

```rust
let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
    // ポーリングループ本体
}));
if let Err(_) = result {
    let _ = tx.send(AppMessage::LiveUpdateError("ポーリングスレッドが異常終了".into()));
}
```

`catch_unwind`は全てのpanicを捕捉できるわけではない（例: `abort`を呼ぶpanic）が、一般的なケースではスレッドの異常終了を安全に処理できる。

## 単体テスト要件

### テストケース1: 3回連続エラーでスレッドが自動停止しErrorメッセージが送信される 🔵

**信頼性**: 🔵 *REQ-LU-101「3回連続エラーで自動停止」より*

**Given**: ポーリング対象のファイルパスが存在しない（またはアクセス権限がない）
**When**: ポーリングスレッドが3回連続でエラーを検出する
**Then**: スレッドが自動停止し、チャネルから`AppMessage::LiveUpdateError`が受信される

**テスト方法**: テンポラリディレクトリに存在しないパスを指定して`start_poller`を呼び出し、エラーメッセージの受信とスレッドの停止を確認する。短いポーリング間隔（例: 50ms）を使用してテスト時間を短縮する。

**テストファイル**: `egui-app/src/io/live_update_poller.rs` (#[cfg(test)] mod tests)

### テストケース2: エラー→成功→エラーの順でカウントがリセットされる 🔵

**信頼性**: 🔵 *EDGE-LU-003「復旧可能性」より*

**Given**: ポーリング対象のファイルが存在する
**When**: 1回エラー（ファイル一時削除）→ ファイル復元で成功（カウントリセット）→ 再度エラー
**Then**: エラーカウントが1に戻り、3回連続にはカウントされない

**テスト方法**: テンポラリファイルを作成し、ポーリング開始後に一時的にファイルをリネームしてから復元する。カウントがリセットされることを、スレッドが停止しないことで間接的に確認する。

### テストケース3: 60秒無変化で完了通知メッセージが送信される 🔵

**信頼性**: 🔵 *REQ-LU-010「60秒無変化で完了通知」より*

**Given**: ポーリング対象のファイルが存在し、内容が変化しない
**When**: 最終変更から60秒が経過する
**Then**: チャネルから`AppMessage::LiveUpdateMaybeComplete`が受信される

**テスト方法**: 完了通知の閾値をテスト用に短く設定できるようにし（例: テスト時は200ms）、現実的なテスト時間で確認する。テスト用に定数または`LiveUpdateContext`のフィールドとして閾値をパラメータ化する。

### テストケース4: ファイル削除検出でエラーカウントが増加する 🔵

**信頼性**: 🔵 *EDGE-LU-001「ファイル削除検出」より*

**Given**: ポーリング対象のファイルが存在し、ポーラーが起動している
**When**: ポーリング中にファイルが削除される
**Then**: `fs::metadata`がエラーを返し、エラーカウントが1増加する

**テスト方法**: テンポラリファイルを作成してポーリング開始後、ファイルを削除する。エラーカウントの増加を確認するため、ファイルを即座に復元してスレッドが停止しないことを確認する（カウント1の状態でリセットされる）。
