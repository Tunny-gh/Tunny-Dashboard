```rust
fn e2e_polling_flow() {
    // 1. テンポラリファイル作成（初期Journal内容を書き込み）
    let dir = tempdir().unwrap();
    let file_path = dir.path().join("test.log");
    let initial_content = create_test_journal(100); // 100件のトライアル
    fs::write(&file_path, &initial_content).unwrap();

    // 2. AppState初期化 + Poller起動
    let mut state = AppState::new();
    state.journal_path = Some(file_path.clone());
    // ... Poller起動 ...

    // 3. ファイルに追記（10件追加）
    let append_content = create_test_trials(10);
    let mut f = OpenOptions::new().append(true).open(&file_path).unwrap();
    f.write_all(append_content.as_bytes()).unwrap();

    // 4. Pollerが検出→LiveUpdateDone生成を待機
    // 5. MessageHandlerでAppState更新
    // 6. trial_rows.len()が110になることを確認
}
```

### 2. ファイル追記→Poller検出→AppState更新の全流れ確認 🔵

**信頼性**: 🔵 *dataflow.md 全フロー統合・acceptance-criteria.md より*

E2Eテストで以下の全流れを検証:

1. Pollerがファイル追記を検出（byte_offset差分）

## テストケース

### TC-001: テンポラリファイルにトライアル追記→Pollerが検出→AppStateが更新される 🔵

**信頼性**: 🔵 *acceptance-criteria.md メインシナリオより*

- **Given**: テンポラリJournalファイルに100件のトライアルが存在、Pollerが起動中
- **When**: ファイルに10件のトライアルを追記
- **Then**: Pollerが追記を検出する
- **And**: `LiveUpdateDone`メッセージが生成される
- **And**: AppStateの`trial_rows`が110件になる
- **And**: Paretoランクが110件で再計算される
- **And**: GPUバッファが再構築される

### TC-002: ファイル削除→3回連続エラー→自動停止 🔵

**信頼性**: 🔵 *EDGE-LU-001・EDGE-LU-101 より*

- **Given**: Pollerがファイルを監視中
- **When**: 監視対象ファイルが削除される
- **Then**: PollerがI/Oエラーを検出する
- **And**: 3回連続でエラー後、Pollerが自動停止する
- **And**: AppStateの`live_update.enabled`は変更されない（ユーザーが意図的にOFFにするまで）

### TC-003: 0バイトファイル→読み込みスキップ 🔵

**信頼性**: 🔵 *EDGE-LU-102 より*

- **Given**: 空ファイル（0バイト）でPollerを起動
- **When**: ポーリング実行
- **Then**: 読み込みバイト数が0のためスキップされる
- **And**: エラーが発生しない
- **And**: ファイルに追記後、次回ポーリングで正常に検出される

### TC-004: 10,000行一括追加→UIフリーズなし 🟡

**信頼性**: 🟡 *NFR-LU-001・NFR-LU-002 はパフォーマンス要件であるが、環境依存の要素が大きいため*

- **Given**: 1,000件のトライアルが存在するStudyContext
- **When**: 10,000件のトライアルを一括追加
- **Then**: MessageHandler処理がメインスレッドで合理的な時間（数百ms以内）で完了する
- **And**: UIスレッドがブロックされない（Poller→Parserは別スレッド）
- **And**: 最終的に`trial_rows`が11,000件になる

### TC-005: パフォーマンステスト: 1,000行差分パース100ms以内 🔵

**信頼性**: 🔵 *NFR-LU-001 より*

- **Given**: 1,000行分のJournal差分データ
- **When**: LogParserでパース実行
- **Then**: パース処理が100ms以内に完了する
- **And**: 正確なTrialRowが生成される

## 注意事項

- 統合テストでは`tempfile`クレートを使用する。`Cargo.toml`の`[dev-dependencies]`に`tempfile = "3"`を追加すること
- テストのタイムアウトに注意する。Pollerのポーリング間隔が1秒の場合、追記検出まで最大1秒待機する。テストでは`std::thread::sleep`で適切な待機を行う
- ファイル削除テストでは、Pollerの自動停止が3回のポーリングサイクル後に発生するため、テストタイムアウトを長めに設定する（例: 10秒）
- パフォーマンステスト（TC-004, TC-005）はCI環境での実行速度変動を考慮し、マージンを持った閾値を設定する
- Windows環境ではファイルロックの挙動が異なるため、ファイル削除テストで`fs::remove_file`のエラーハンドリングに注意する
