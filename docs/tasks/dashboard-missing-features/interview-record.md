# dashboard-missing-features タスク分割ヒアリング記録

**作成日**: 2026-05-12
**ヒアリング実施**: step4 タスク分割方針確認

## ヒアリング目的

設計文書に基づく実装タスク分割にあたり、1日単位の粒度、フェーズ順序、テスト厚み、Surface Plot のスコープを明確化するためにヒアリングを行った。

---

## 質問と回答

### Q1: 作業規模

**質問日時**: 2026-05-12  
**カテゴリ**: タスク粒度  
**背景**: `kairo-tasks` の出力粒度を決めるために、詳細分割か軽量分割かの確認が必要だった。

**回答**: 詳細タスク分割（推奨）

**信頼性への影響**:

- 各タスクに実装詳細、単体テスト、統合テスト、UI/UX 要件を含める方針を確定した。
- タスクファイルは `full_task_template` 相当の構成で作成する。

---

### Q2: タスク粒度

**質問日時**: 2026-05-12  
**カテゴリ**: タスク粒度  
**背景**: 8機能を横断しているため、半日単位まで細かく切るか、1日単位でまとめるかを決める必要があった。

**回答**: 1日単位で問題ない

**信頼性への影響**:

- 1タスクあたりの推定工数は原則 8 時間で設計する方針を確定した。
- 小さすぎる変更は統合し、1日で意味のある成果物が出るタスクにまとめる。

---

### Q3: 実装優先順位

**質問日時**: 2026-05-12  
**カテゴリ**: 優先順位  
**背景**: 本件は `AppState`・`ToolbarAction`・比較ローダー・描画ルーティングが互いに依存するため、フェーズ順序の合意が必要だった。

**回答**: 基盤→状態管理→UI→統合

**信頼性への影響**:

- フェーズ分割をレイヤー基準で行う方針を確定した。
- Phase 1 を基盤・状態、Phase 2 を操作 UI、Phase 3 を高度可視化、Phase 4 をエクスポート統合・検証とする根拠になった。

---

### Q4: テスト要件

**質問日時**: 2026-05-12  
**カテゴリ**: テスト要件  
**背景**: デスクトップ UI で E2E が重くなりやすいため、単体テストと統合テストの比重を先に確認する必要があった。

**回答**: 標準レベル

**信頼性への影響**:

- 主要ロジックは単体テスト、重要な機能連携のみ統合テストとする方針を確定した。
- 各タスクのテスト要件は「純関数/状態遷移の単体テスト + 代表的な連携確認」に絞る。

---

### Q5: Surface Plot のスコープ

**質問日時**: 2026-05-12  
**カテゴリ**: 技術制約  
**背景**: 設計文書では Phase 1 を Heatmap/Contour に限定している一方、将来の 3D 拡張を今回の分割に含めるか確認が必要だった。

**回答**: 3D調査タスクも含める

**信頼性への影響**:

- Surface Plot 実装タスクとは別に、3D 描画方式の調査・最小プロトタイプを 1 タスクとして分離する方針を確定した。
- Surface Plot 関連は「基盤」「Heatmap/Contour 実装」「3D調査」の 3 タスクに分割する。

---

## ヒアリング結果サマリー

### 確認できた事項

- タスク粒度は 1 日単位でよい
- フェーズ順序はレイヤー順を優先する
- テストは高カバレッジよりも主要ロジックと代表的統合を優先する
- Surface Plot は本実装に加えて 3D 調査タスクを含める

### 設計文書との差分

- 設計文書では Surface Plot は Phase 1 の Heatmap/Contour 完了を主スコープとしていたが、タスク分割では将来の wgpu 3D 拡張を見据えた調査タスクを追加する
- それ以外の方針は設計文書と整合している

### 残課題

- PNG キャプチャ API の詳細は実装時に利用中の eframe API を確認する必要がある
- Surface Plot 3D 調査は「実装可否の判断材料」を成果物とし、本開発スコープとは分離して扱う
