# rayon 導入による並列化高速化 要件定義書

## 概要

`rayon` は既に `rust_core/Cargo.toml` に依存関係として追加されており、現在は
`pdp/kriging_core.rs` の PDP グリッド計算（4 箇所）でのみ使用されている。
本要件定義は、未並列化の計算ヘビーパス（感度分析の目的変数ループ、Sobol サロゲート、
RandomForest 木構築、Permutation 特徴量ループ）に rayon を展開し、
ユーザー体感レスポンスを改善することを目的とする。

## 機能要件（EARS 記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: PRD・設計文書・ユーザヒアリングを参考にした確実な要件
- 🟡 **黄信号**: 設計文書・ユーザヒアリングから妥当な推測による要件
- 🔴 **赤信号**: PRD・設計文書・ユーザヒアリングにない推測による要件

---

### 通常要件

- **REQ-001**: システムは `sensitivity/analysis/common.rs` の `run_tree_metric_for_all_objectives` において目的変数ごとのループを `rayon::par_iter()` で並列実行しなければならない。  
  🔵 *ユーザヒアリング（適用範囲：Sensitivity 目的変数ループ）・コードベース調査より*

- **REQ-002**: システムは `sensitivity/sobol.rs` の `build_sobol_surrogate` において `y_matrix` ループを `rayon::par_iter()` で並列実行しなければならない。  
  🔵 *ユーザヒアリング（適用範囲：Sobol サロゲート per-objective）・コードベース調査より*

- **REQ-003**: システムは `core/random_forest/forest.rs` の `RandomForest::train` において木構築ループを `rayon` で並列実行しなければならない。  
  🔵 *ユーザヒアリング（適用範囲：RandomForest 木構築ループ）・コードベース調査より*

- **REQ-004**: システムは `sensitivity/permutation.rs` の `compute_from_prepared` において特徴量ループを並列実行できるよう in-place 変更パターンを再構成した上で `rayon::par_iter()` を適用しなければならない。  
  🔵 *ユーザヒアリング（適用範囲：Permutation 特徴量ループ）・コードベース調査より*

---

### 条件付き要件

- **REQ-101**: LightGBM を使用する感度分析メトリクス（SHAP・MDI・PFI・RfAnova）において、目的変数ごとに独立したモデルインスタンスを並列訓練する場合、システムは LightGBM C API の「モデルインスタンス間は独立してスレッドセーフ」という前提のもとで並列化しなければならない。  
  🔵 *ユーザヒアリング（LGBM スレッド安全性：並列訓練を許可）・LightGBM C API 仕様より*

- **REQ-102**: `RandomForest::train` を並列化する場合、システムはスレッドごとに異なる決定論的シード（`seed + tree_index` など）を使って各木の `Lcg` RNG を初期化しなければならない。  
  🔵 *コードベース調査（現行 LCG シード設計）より*

- **REQ-103**: `Permutation` の特徴量ループを並列化する場合、システムは各スレッドが評価行列のコピーを独立して保持することで、in-place 変更の競合を排除しなければならない。  
  🟡 *コードベース調査（`x_eval_work` in-place 設計）から妥当な推測*

---

### 状態要件

- **REQ-201**: 既存の全ユニットテストが `cargo test` で引き続き通過している状態において、システムは並列化コードを本番ブランチに統合しなければならない。  
  🔵 *ユーザヒアリング（安全検証：既存テストの通過で十分）より*

---

### オプション要件

- **REQ-301**: システムは `rayon::ThreadPoolBuilder` を使って rayon グローバルスレッドプール数を設定する機能を提供してもよい（現時点では egui 競合回避のための制限は不要）。  
  🟡 *ユーザヒアリング（egui スレッド：変更不要）より。将来的なチューニング余地として記載*

---

### 制約要件

- **REQ-401**: システムは egui UI スレッドへの rayon スレッドプール制限を行わない（現行の非同期呼び出し構造のまま維持する）。  
  🔵 *ユーザヒアリング（egui スレッド：変更不要）より*

- **REQ-402**: `rayon = "1"` の依存バージョンは変更しない（既に `rust_core/Cargo.toml` に存在）。  
  🔵 *コードベース調査（Cargo.toml）より*

## 非機能要件

### パフォーマンス

- **NFR-001**: 目的変数が N 個（N ≥ 2）の場合、感度分析（RfAnova/MDI/SHAP/Permutation/Sobol）の計算時間が並列化前と比較して概ね N 倍以内に削減されることが期待される。  
  🟡 *rayon の並列性能特性から妥当な推測。実測はベンチマークで確認*

- **NFR-002**: ベンチマーク対象モジュールに対して `criterion` ベンチマークスイートのカバレッジを追加し、並列化の効果を定量化しなければならない。  
  🔵 *ユーザヒアリング（ベンチマーク：含める）より*

- **NFR-003**: 目的変数が 1 個のシングルオブジェクティブケースにおいて、並列化によるオーバーヘッドが計算時間を増加させないこと（rayon の逐次フォールバックを利用すること）。  
  🟡 *rayon の一般的動作特性から妥当な推測*

### 正確性・再現性

- **NFR-101**: 並列化後、既存の `cargo test` テストスイートが引き続き通過すること。  
  🔵 *ユーザヒアリング（安全検証）より*

- **NFR-102**: `RandomForest::train` の並列化において、木ごとのシードが決定論的に計算されること（同一入力で同一モデルが得られること）。  
  🟡 *シード管理設計から妥当な推測。浮動小数点加算順が変わるため完全一致は保証しないが、統計的性質は維持*

### 保守性

- **NFR-201**: 並列化対象のコードは `rayon::prelude::*` の `use` 宣言を各ファイルの先頭に集約し、利用個所を明示すること。  
  🔵 *既存 `pdp/kriging_core.rs` の実装パターンより*

## Edge ケース

### エラー処理

- **EDGE-001**: LightGBM 訓練が失敗した場合（`None` を返す場合）、並列実行中でも `unwrap_or_else` / `unwrap_or` で安全にフォールバックし、パニックしてはならない。  
  🔵 *既存コードの `Option` 返却設計より*

- **EDGE-002**: `Permutation` 特徴量ループを並列化した場合、評価データのコピーコストが許容範囲内であること（大規模データで性能劣化しないこと）。  
  🟡 *Permutation in-place 設計から妥当な推測*

### 境界値

- **EDGE-101**: 目的変数が 1 個のケース（シングルオブジェクティブ）でも動作すること。  
  🔵 *既存テストケースより*

- **EDGE-102**: データ行数が最小（n < 2）の場合、並列化パスは早期リターンし rayon を起動しないこと。  
  🔵 *既存コードのガード処理より*
