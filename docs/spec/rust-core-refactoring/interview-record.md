# rust-core リファクタリング ヒアリング記録

**作成日**: 2026-05-14
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング

## ヒアリング目的

コード分析（Explore エージェントによる全モジュール調査）で発見した 25 個の問題点を基に、
優先順位・API 互換性方針・設計アプローチを確認するためのヒアリングを実施した。

---

## 質問と回答

### Q1: リファクタリングの最優先カテゴリ

**カテゴリ**: 優先順位
**背景**: 25 個の問題点を「コード重複排除」「責務分離」「効率改善」「命名・可読性」の 4 カテゴリに分類し、
スコープを絞るために質問した。

**回答**: コード重複排除・責務分離・効率改善（複数選択）

**信頼性への影響**:
- REQ-A01〜A07（重複排除）が 🔴 → 🔵 に向上
- REQ-B01〜B05（責務分離）が 🔴 → 🔵 に向上
- REQ-C01〜C08（効率改善）が 🔴 → 🔵 に向上
- 命名・可読性（Finding 19〜22）はスコープ外として要件から除外

---

### Q2: 公開 API の互換性

**カテゴリ**: 影響範囲
**背景**: `SamplingContext` 移行や `GpModel` 分離は `egui-app` 側の呼び出しコードも変更する必要があり、
破壊的変更の許容度を確認した。

**回答**: 破壊的変更 OK（egui-app 側も含めてすべて修正する）

**信頼性への影響**:
- REQ-C05〜C08（SamplingContext 移行）が 🟡 → 🔵 に向上（egui-app 側変更が確定）
- REQ-B05（GpModel 分離）の実装範囲が確定（🟡 のまま、GP は内部のみ公開なので影響小）

---

### Q3: SensitivityMetric トレイトパターンの導入

**カテゴリ**: 設計アプローチ
**背景**: `sensitivity/mod.rs` が既に `SensitivityMetric` を型として再エクスポートしているが、
コード分析では `full.rs` の 7 アーム match がトレイトでなく直接呼び出しであることを確認。
統一インターフェースとしてトレイトを導入するか確認した。

**回答**: 導入する（推奨）

**信頼性への影響**:
- REQ-A01, A03（トレイト導入）が 🔴 → 🔵 に向上

---

### Q4: サンプリングのグローバル状態廃止

**カテゴリ**: 設計アプローチ
**背景**: `sampling/state.rs` がグローバル Mutex 変数で状態管理していることを確認。
WASM 不要なためグローバル状態の理由がなく、`SamplingContext` 構造体への移行を提案した。

**回答**: SamplingContext 構造体に移行

**信頼性への影響**:
- REQ-C05〜C08 が 🔴 → 🔵 に向上

---

## ヒアリング結果サマリー

### 確認できた事項
- コード重複排除・責務分離・効率改善が最優先（命名改善はスコープ外）
- 公開 API の破壊的変更は許容（egui-app 側も同時修正）
- `SensitivityMetric` トレイト導入に合意
- `SamplingContext` 構造体への移行に合意

### 追加/変更要件
- `SensitivityMetric` トレイト（新規追加） → REQ-A01〜A03
- `SamplingContext` 構造体（新規追加） → REQ-C05〜C08
- egui-app 側の `SamplingContext` 対応が要件に追加 → REQ-C08

### 残課題
- `data/dataframe/state.rs` のグローバル DataFrame 状態は今回スコープ外（egui-app との結合度が高く別途検討が必要）
- `GpModel` 分離（REQ-B05）は内部 API のため影響範囲が小さく、優先度中程度
- LightGBM FFI の `lgbm_sys.rs` はスコープ外（条件付きコンパイルが複雑）
