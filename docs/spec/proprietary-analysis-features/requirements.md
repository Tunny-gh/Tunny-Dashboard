# プロプライエタリ分析ツール不足機能 要件定義書

## 概要

Tunny Dashboard が商用最適化ツール（プロプライエタリな汎用最適化ソフト等）と同等の分析機能を提供するために不足している機能を定義する。READMEおよび `docs/spec/first_spec.md` の差別化ポイントと、egui-app の実装調査結果に基づく。

- **対象**: Tunny Dashboard（Rust/egui デスクトップアプリ）
- **技術スタック**: Rust (egui-app) + rust_core（分析ライブラリ共有）
- **調査日**: 2026-04-26

### REQ-001: Trade-off Navigator（重み付きParetoナビゲーター）

**優先度**: Must Have

#### 通常要件

- REQ-001-A: 多目的解析モード時（目的数 ≥ 2）、システムは Left Panel 下部に「Trade-off Navigator」セクションを表示しなければならない 🔵 *ユーザヒアリング Q4・first_spec.md 差別化ポイントより*
- REQ-001-B: Trade-off Navigator セクションは、各目的関数に対応する重みスライダー（0.0〜1.0）を表示しなければならない 🔵 *ユーザヒアリング Q4・tradeoff.rs 実装より*
- REQ-001-C: 重みスライダーの合計が常に 1.0 になるよう、システムは他スライダーを自動正規化しなければならない 🟡 *チェビシェフスカラー化の要件から妥当な推測*

#### 条件付き要件

- REQ-001-D: ユーザーが重みスライダーを変更した場合、システムは `score_tradeoff_navigator(weights)` を呼び出し最良解インデックスをリアルタイム更新しなければならない 🔵 *tradeoff.rs 実装・ユーザヒアリング Q4 より*
- REQ-001-E: 最良解が確定した場合、システムはその試行を全グラフで **ゴールドスター（★）** でハイライト表示しなければならない 🟡 *プロプライエタリソフト参考・妥当な推測*
- REQ-001-F: 単目的モード時（目的数 = 1）、システムは Trade-off Navigator セクションを非表示にしなければならない 🔵 *ユーザヒアリング Q4 より（多目的限定）*

#### 状態要件

- REQ-001-G: Trade-off Navigator の重みは分析セッション保存（REQ-004）に含まれなければならない 🔵 *ユーザヒアリング Q3・セッション永続化仕様より*

### REQ-002: フィルタ条件の保存・復元

**優先度**: Must Have

#### 通常要件

- REQ-002-A: システムは ToolBar に「フィルタを保存」ボタンを提供しなければならない 🔵 *ユーザヒアリング Q3・first_spec.md UI機能より*
- REQ-002-B: 「フィルタを保存」時、システムは `filterRanges`・`selectedIndices`・`colorMode` を JSON ファイルとしてダウンロードしなければならない 🔵 *ユーザヒアリング Q3・filter.rs 実装より*
- REQ-002-C: システムは ToolBar に「フィルタを読み込み」ボタンを提供しなければならない 🔵 *ユーザヒアリング Q3 より*

#### 条件付き要件

- REQ-002-D: ユーザーがフィルタ JSON を読み込んだ場合、システムは `filterRanges` を `filter.rs` の `SelectionStore` に適用し全グラフを更新しなければならない 🔵 *filter.rs 実装・ユーザヒアリングより*
- REQ-002-E: 読み込んだ JSON の変数名・目的名が現在の Study と一致しない場合、システムは不一致のフィルタ項目をスキップしユーザーに警告を表示しなければならない 🟡 *Study 切り替え仕様から妥当な推測*

### REQ-003: レイアウト設定の保存・読み込み

**優先度**: Must Have

#### 通常要件

- REQ-003-A: システムは ToolBar に「レイアウトを保存」ボタンを提供しなければならない 🔵 *ユーザヒアリング Q3・first_spec.md UI機能より*
- REQ-003-B: 「レイアウトを保存」時、システムは `LayoutState`（レイアウトモード・グリッド構成・各チャート設定）を JSON ファイルとして保存しなければならない 🔵 *layout_state.rs 実装・ユーザヒアリングより*
- REQ-003-C: システムは ToolBar に「レイアウトを読み込み」ボタンを提供しなければならない 🔵 *ユーザヒアリング Q3 より*

#### 条件付き要件

- REQ-003-D: ユーザーがレイアウト JSON を読み込んだ場合、システムはグリッド構成を復元し Mode D に切り替えなければならない 🔵 *layout_state.rs 実装・ユーザヒアリングより*
- REQ-003-E: 保存された JSON に含まれない ChartId が存在する場合（将来の下位互換）、システムはそのセルをスキップして残りを復元しなければならない 🟡 *互換性要件として妥当な推測*

### REQ-004: 分析セッション永続化

**優先度**: Must Have

#### 通常要件

- REQ-004-A: システムは ToolBar に「セッションを保存（.tdash）」ボタンを提供しなければならない 🔵 *ユーザヒアリング Q3・note.md セッション仕様より*
- REQ-004-B: .tdash ファイルは `version`・`created_at`・`journal_filename`・`selected_study_id`・`filter_ranges`・`selected_indices`・`color_mode`・`cluster_config`・`layout_mode`・`layout_config`・`pinned_trials`・`tradeoff_weights` を含まなければならない 🔵 *ユーザヒアリング Q3・note.md セッション仕様より*

#### 条件付き要件

- REQ-004-C: ユーザーが .tdash ファイルを読み込んだ場合、システムは Journal ファイルの再選択を促さず、セッション内の `journal_filename` と一致するファイルが開いている場合に自動復元しなければならない 🔵 *ユーザヒアリング Q3・分析再開ユースケースより*
- REQ-004-D: Journal ファイルが一致しない場合、システムはフィルタ・レイアウト設定のみを復元し、データを再読み込みするよう案内しなければならない 🟡 *妥当な移植性要件として推測*

### REQ-005: HTML レポート生成・エクスポート

**優先度**: Must Have

#### 通常要件

- REQ-005-A: システムは Export パネル内（現行の CSV エクスポートボタンの隣）に「HTML レポート出力」ボタンを追加しなければならない 🔵 *ユーザヒアリング Q5 より*
- REQ-005-B: HTML レポートには以下のセクションを含まなければならない：スタディ情報サマリー・現在表示中のチャートの SVG キャプチャ・選択試行のサマリーテーブル・統計情報（平均・分散・Pareto 数） 🔵 *ユーザヒアリング Q5 より*
- REQ-005-C: HTML レポートは単一のスタンドアロン HTML ファイル（埋め込み CSS 含む）として出力されなければならない 🔵 *first_spec.md エクスポート仕様・ユーザヒアリング Q5 より*

#### 条件付き要件

- REQ-005-D: HTML レポート生成時、システムは現在フィルタで選択されている試行のみをサマリーテーブルに含めなければならない 🔵 *ユーザヒアリング Q5・フィルタ連動の設計方針より*

#### 制約要件

- REQ-005-E: インタラクティブ HTML（Plotly/deck.gl 埋め込み）は本スコープ対象外とする 🔵 *ユーザヒアリング Q5 明示的にスコープ外と確認*

### REQ-006: 複数 Study 比較 UI

**優先度**: Must Have

#### 通常要件

- REQ-006-A: システムは Study 比較モードを提供しなければならない。比較モードでは 2〜4 件の Study を同時に選択できる 🔵 *ユーザヒアリング Q7・first_spec.md Study比較設計より*
- REQ-006-B: 比較モードでは、以下 4 種の比較ビューを提供しなければならない：
  1. 統計サマリー比較テーブル（試行数・Pareto数・Best値・平均値）
  2. HV 履歴重畳グラフ（各 Study を異なる色の折れ線で表示）
  3. Pareto フロント重畳散布図（各 Study を異なる色で表示）
  4. 変数分布図 KDE 重畳（各 Study の変数分布を重ねて表示）
  🔵 *ユーザヒアリング Q7 より*

#### 条件付き要件

- REQ-006-C: 比較対象 Study の目的関数数が異なる場合、システムは共通の目的関数軸のみで比較し、非共通軸はグレーアウトで表示しなければならない 🟡 *Study 比較の技術制約から妥当な推測*
- REQ-006-D: 比較モード中に Brushing 操作を行った場合、システムはすべての選択中 Study に対して同一フィルタを適用しなければならない 🟡 *Brushing & Linking 設計から妥当な推測*

### REQ-007: アーティファクト連携

**優先度**: Must Have

#### 通常要件

- REQ-007-A: システムは Journal ファイルの読み込み時、同一ディレクトリの `artifacts/` フォルダを自動検出しなければならない（デフォルト動作） 🔵 *ユーザヒアリング Q6 より*
- REQ-007-B: ToolBar に「Artifacts フォルダを選択」ボタンを提供し、自動検出パスを手動上書きできなければならない 🔵 *ユーザヒアリング Q6 より*
- REQ-007-C: Trial Table に「Artifacts」列を追加し、artifact_id に対応するファイルが存在する場合はファイルタイプアイコンを表示しなければならない 🔵 *ユーザヒアリング Q3・first_spec.md アーティファクト設計より*

#### 条件付き要件

- REQ-007-D: ユーザーが Trial Table の Artifacts 列アイコンをクリックした場合、システムはモーダルでプレビューを表示しなければならない 🔵 *ユーザヒアリング Q3 より*
- REQ-007-E: PNG/JPG ファイルの場合、システムはインライン画像プレビューを表示しなければならない 🔵 *ユーザヒアリング Q3 より*
- REQ-007-F: CSV ファイルの場合、システムは先頭 100 行のテーブルプレビューを表示しなければならない 🔵 *ユーザヒアリング Q3 より*
- REQ-007-G: その他のファイル形式の場合、システムはファイル名とサイズを表示しダウンロードリンクを提供しなければならない 🟡 *アーティファクト設計から妥当な推測*

#### 状態要件

- REQ-007-H: `artifacts/` フォルダが存在しない場合、システムは Artifacts 列を非表示にしなければならない 🟡 *妥当なフォールバック動作として推測*

## 非機能要件

### パフォーマンス

- NFR-001: Trade-off Navigator の重みスライダー変更から全グラフハイライト更新まで、50,000 試行で 100ms 以内に完了しなければならない 🔵 *tradeoff.rs の WASM 実装・パフォーマンス設計より*
- NFR-002: フィルタ・レイアウト・セッション JSON の保存/読み込み操作は 1 秒以内に完了しなければならない 🟡 *UI レスポンス基準から妥当な推測*
- NFR-003: HTML レポート生成（SVG キャプチャ + テーブル）は 30,000 選択試行に対して 10 秒以内に完了しなければならない 🟡 *レポート生成の性質から妥当な推測*

### ユーザビリティ

- NFR-101: フィルタ・レイアウト・セッション保存ダイアログは OS ネイティブのファイル保存ダイアログを使用しなければならない 🔵 *egui のネイティブ実装ポリシーより*
- NFR-102: 複数 Study 比較モードでは、各 Study の色が凡例と一致し、すべての比較ビューで統一されなければならない 🟡 *可視化の一貫性から妥当な推測*

### セキュリティ

- NFR-201: アーティファクトファイルの読み込みは egui のファイル選択 API を通じてのみ行い、パストラバーサルを防止しなければならない 🔵 *セキュリティ基準・OWASP より*
- NFR-202: .tdash セッションファイルのデシリアライズは既知のフィールドのみを受け入れ、不明なフィールドは無視しなければならない（serde の `deny_unknown_fields` 等） 🟡 *デシリアライズセキュリティから妥当な推測*

## Edge ケース

### エラー処理

- EDGE-001: .tdash セッションファイルのバージョンが現在と異なる場合、システムは互換フィールドのみ復元し未知フィールドを無視しなければならない 🟡 *下位互換性要件から推測*
- EDGE-002: Trade-off Navigator でスライダーをすべて 0 に設定しようとした場合、システムは最後の変更を取り消して直前の有効な重み配分を維持しなければならない 🟡 *重み正規化の数値安定性から推測*
- EDGE-003: アーティファクトファイルが読み込み時に削除・移動されていた場合、システムは「ファイルが見つかりません」メッセージをモーダルに表示しなければならない 🔵 *ファイル操作のエラー処理から確実*
- EDGE-004: 複数 Study 比較で選択した Study 間に共通の目的関数軸が 1 つもない場合、システムは比較モードへの移行を拒否しエラーメッセージを表示しなければならない 🟡 *比較機能の技術制約から推測*

### 境界値

- EDGE-101: Trade-off Navigator は目的数が 2〜4 の範囲でのみ動作し、5 目的以上の Study では表示しないこと 🟡 *first_spec.md の対象規模「最大4目的」から妥当な推測*
- EDGE-102: HTML レポートで選択試行が 0 件の場合、システムはサマリーテーブルを空テーブルとして出力し、ユーザーに選択が 0 件であることを HTML 内に注記しなければならない 🟡 *エクスポートの境界値から妥当な推測*
