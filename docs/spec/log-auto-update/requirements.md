# Log Auto Update 要件定義書

## 概要

Optuna Journal形式（.log）ファイルの自動更新機能。最適化実行中にファイルへ追記される新規トライアルを、ユーザー操作を妨げることなくリアルタイムに反映する。

ネイティブデスクトップアプリ（Rust egui）向けのファイルポーリングベースの実装。既存の `append_journal_diff` コア差分パーサー、`LiveUpdateState`、`AppMessage::LiveUpdateDone` を活用し、不足しているポーリングループとメッセージハンドラー統合を実装する。

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: PRD・EARS要件定義書・設計文書・ユーザヒアリングを参考にした確実な要件
- 🟡 **黄信号**: PRD・EARS要件定義書・設計文書・ユーザヒアリングから妥当な推測による要件
- 🔴 **赤信号**: PRD・EARS要件定義書・設計文書・ユーザヒアリングにない推測による要件

### 通常要件

- REQ-LU-001: システムは ポーリング方式でファイルサイズの変化を検出し、増加分のバイトのみを読み込んで差分パースしなければならない 🔵 *既存実装 live_update.rs + ヒアリング「ポーリング方式」より*
- REQ-LU-002: システムは ポーリング間隔をデフォルト2秒とし、ユーザーが1秒〜30秒の範囲で調整できるUIを提供しなければならない 🔵 *既存 LiveUpdateState.interval_ms + ヒアリング「間隔調整UI」より*
- REQ-LU-003: システムは ツールバーの「Live: On/Off」トグルでライブ更新の開始・停止を制御しなければならない 🔵 *既存 toolbar.rs ToggleLiveUpdate より*
- REQ-LU-004: システムは ファイルが開かれていない状態ではライブ更新トグルを無効化しなければならない 🔵 *ヒアリング「トグルのみで開始」より*
- REQ-LU-005: システムは トグルON時に現在開いているJournalファイルのパスを自動的に監視対象として設定しなければならない 🔵 *ヒアリング「トグルのみで開始」+ 既存 LiveUpdateState.file_path より*
- REQ-LU-006: システムは ライブ更新中、ユーザーのBrushing選択・フィルタ設定・ズーム視点を変更してはならない 🔵 *既存要件 REQ-134 + ヒアリング「全保持」より*
- REQ-LU-007: システムは 新規トライアル追加時、現在表示中のStudyのグラフ・テーブル・カウンタを再描画しなければならない 🔵 *ヒアリング「全Study更新」+ 既存 LiveUpdateDone メッセージより*
- REQ-LU-008: システムは 全Studyのトライアル数を更新し、Study選択ドロップダウンの件数表示もリアルタイムに反映しなければならない 🔵 *ヒアリング「全Study更新」より*
- REQ-LU-009: システムは ツールバーに現在の完了トライアル数を表示しなければならない 🔵 *ヒアリング「試行数カウンタ」より*
- REQ-LU-010: システムは ライブ更新中のファイル読み込みエラーが3回連続で発生した場合、自動的にポーリングを停止しエラーメッセージを表示しなければならない 🔵 *既存 TASK-1201設計 + ヒアリング「自動停止あり」より*

### 条件付き要件

- REQ-LU-101: ポーリングでファイルサイズが変化しない場合、システムはポーリングを継続しつつ、一定時間（60秒）変化なしの場合はステータスバーに「最適化が完了した可能性があります」を通知してもよい 🔵 *ヒアリング「通知のみ」より*
- REQ-LU-102: ポーリングで新規完了トライアルが0件の場合、システムはグラフの再描画をスキップし不要なUI更新を回避しなければならない 🟡 *パフォーマンス要件から妥当な推測*
- REQ-LU-103: Journalファイルに複数Studyが含まれる場合、システムは全Studyの差分をパースし、それぞれのメタデータを更新しなければならない 🔵 *ヒアリング「全Study更新」+ 既存パーサー設計より*
- REQ-LU-104: 書き込み途中の不完全なJSON行はスキップし、次回ポーリングで再読み込みを試みなければならない 🔵 *既存要件 REQ-133 + find_consumed_bytes() 実装より*

### 状態要件

- REQ-LU-201: ライブ更新が有効な状態でユーザーが別のJournalファイルを開いた場合、システムは古いファイルの監視を停止し、新しいファイルの監視を開始しなければならない 🟡 *既存コードフローから妥当な推測*
- REQ-LU-202: ライブ更新が有効な状態でユーザーがStudyを切り替えた場合、システムはポーリングを継続し、切り替え後のStudyデータを更新しなければならない 🟡 *既存コードフローから妥当な推測*
- REQ-LU-203: アプリケーション終了時、システムはバックグラウンドのポーリングスレッドを確実に停止しなければならない 🔵 *ネイティブアプリの基本要件より*

### オプション要件

- REQ-LU-301: システムは ポーリング間隔調整UIをツールバーまたは設定パネルに提供してもよい 🔵 *ヒアリング「間隔調整UI」より*
- REQ-LU-302: システムは ライブ更新の累積統計（総更新回数、総追加トライアル数）を表示してもよい 🟡 *UX改善の推測*

### 制約要件

- REQ-LU-401: システムは ポーリングループをメインUIスレッドから分離したバックグラウンドスレッドで実行しなければならない 🔵 *既存 spawn_task パターン + thread_local! 制約より*
- REQ-LU-402: システムは thread_local! で管理されるDataFrameとパーサー状態にアクセスするため、ポーリングスレッド内で完結する設計としなければならない 🔵 *既存 rust_core/data/dataframe.rs thread_local! 設計より*
- REQ-LU-403: 差分パース（1,000行）の合計処理時間は100ms以内としなければならない 🔵 *既存非機能要件 NFR-008 より*
- REQ-LU-404: ポーリングによるファイル読み込みは差分バイト範囲のみとし、全件再パースを行ってはならない 🔵 *既存要件 REQ-132 より*

## 非機能要件

### パフォーマンス

- NFR-LU-001: ポーリングのファイルサイズ確認は1ms以内に完了しなければならない 🔵 *std::fs::metadata パフォーマンスより*
- NFR-LU-002: 差分読み込み＋パース（1,000行）の合計処理時間は100ms以内としなければならない 🔵 *既存 NFR-008 + tc_1201_p01 パフォーマンステストより*
- NFR-LU-003: UI再描画は新規完了トライアルが存在する場合のみトリガーし、無駄なフレーム更新を避けなければならない 🟡 *パフォーマンス設計から推測*

### セキュリティ

- NFR-LU-101: 監視対象ファイルはユーザーが明示的に開いたJournalファイルのみとし、任意のファイルパスを監視してはならない 🔵 *既存 rfd::FileDialog によるユーザー選択より*

### ユーザビリティ

- NFR-LU-201: ライブ更新のON/OFF操作は1クリックで完結しなければならない 🔵 *既存トグルUIより*
- NFR-LU-202: ライブ更新状態（ON/OFF、エラー、試行数）はツールバーから常に確認可能でなければならない 🔵 *ヒアリング「試行数カウンタ」より*

## Edgeケース

### エラー処理

- EDGE-LU-001: ファイルがポーリング中に削除された場合、システムは自動停止し「ファイルが見つかりません」エラーを表示しなければならない 🔵 *OS ファイル操作の基本ケースより*
- EDGE-LU-002: ファイルの読み取り権限がなくなった場合、システムはエラーカウントを増やし3回連続で自動停止しなければならない 🟡 *REQ-LU-010 からの派生*
- EDGE-LU-003: ポーリングスレッドがpanicした場合、システムはライブ更新を無効化しUIにエラーを表示しなければならない 🟡 *Rust スレッド設計から推測*

### 境界値

- EDGE-LU-101: ファイルサイズが0バイトの場合、ポーリングはスキップし次回を待機しなければならない 🔵 *find_consumed_bytes() の設計より*
- EDGE-LU-102: ポーリング間隔を最小値（1秒）に設定した場合でも、UIスレッドのレスポンスに影響を与えてはならない 🟡 *バックグラウンドスレッド設計から推測*
- EDGE-LU-103: 大量の新規トライアル（10,000行以上）が一度に追加された場合でも、UIがフリーズしてはならない 🟡 *パフォーマンス境界値*

## アーキテクチャ上の制約

### thread_local! 対応

`rust_core` の DataFrame と LiveUpdateState は `thread_local!` で管理されている。ポーリングスレッドは以下の制約を満たさなければならない：

1. ポーリングスレッドは一貫したスレッドIDで動作し、thread_local! の状態を維持する 🔵 *既存コード設計より*
2. `append_journal_diff` の呼び出しはポーリングスレッド内で行う 🔵 *既存 thread_local! 設計より*
3. パース結果は `AppMessage::LiveUpdateDone` としてメインスレッドに送信する 🔵 *既存メッセージパッシングパターンより*

### 既存実装の活用

| コンポーネント | 既存状態 | 活用方法 |
|---|---|---|
| `append_journal_diff()` | 実装済み（テスト含む） | ポーリングループから呼び出し |
| `LiveUpdateState` | state定義済み | `last_byte_offset` で差分管理 |
| `AppMessage::LiveUpdateDone` | メッセージ型定義済み | ハンドラーを実装 |
| `ToolbarAction::ToggleLiveUpdate` | トグルUI実装済み | ポーリング開始/停止を接続 |
| `MessageHandler::LiveUpdateDone` | TODOプレースホルダー | UI更新ロジックを実装 |
