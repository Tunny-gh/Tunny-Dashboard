## ヒアリング目的

PRD（`memory-efficiency-requirements.md`）は MEM-001〜007 を具体的なファイル参照付きで定義しているため、要件としては高信頼。本ヒアリングでは、(1) コード調査で判明した設計上の制約に対する方針確認、(2) 受け入れ基準の検証方法、の差分を明確化した。

### Q3: MEM-001 の「共有カラム表現」実現方針

**質問日時**: 2026-05-29
**カテゴリ**: 未定義部分詳細化
**背景**: コード調査で **列指向 `DataFrame` が `rust_core` の thread_local（ワーカースレッド上）に存在し、UI スレッドから直接借用できない** ことが判明（`dataframe/state.rs:12-21`）。これが `trial_rows` 複製（`io/study.rs:46-94`）の根本原因であり、「共有カラム表現」を成立させるにはアーキテクチャ上の選択が必要。選択肢: (a) `Arc` 等で共有ストア化し thread_local を廃止、(b) `StudyContext` 内を軽量カラム構造に置換、(c) 結果のみ規定し手段は設計フェーズに委譲。

**回答**: 共有ストア化（Arc）— thread_local を廃止し、DataFrame を `Arc` 等で UI/ワーカー両スレッドから安全に読めるようにする。

**信頼性への影響**: REQ-002・REQ-003 を 🔵 で確定。MEM-001 の実装方向が明確化され、設計フェーズの探索範囲が縮小。

---

### Q4: 「メモリ削減」の検証方法

**質問日時**: 2026-05-29
**カテゴリ**: 未定義部分詳細化
**背景**: PRD は「定常 -50% 以上」「~17.6MB/widget」等の数値目標を持つが、測定対象データセット・測定手段が未定義。

**回答**: 定量ベンチマーク必須 — 100k trials × 約22列の代表データセットで改修前後の定常・ピークメモリを測定し、PRD の削減率を数値検証する。

**信頼性への影響**: NFR-004 を 🔵 で追加。受け入れ基準に定量計測タスクを組み込み。代表ベンチマークデータセットの用意が前提タスク（prep.md）として顕在化。

---

### Q5: 「現行機能・分析結果の等価性」リグレッション検証方法

**質問日時**: 2026-05-29
**カテゴリ**: 影響範囲確認
**背景**: REQ-401（機能等価性維持）の検証手段を確定するため。

**回答**: 既存テストスイートで担保 — `cargo test --workspace` のパスを等価性の主証拠とする。
