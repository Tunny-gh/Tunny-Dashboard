# memory-efficiency 準備タスク（ユーザー作業）

> **仕様**: [requirements.md](requirements.md)
> **生成日**: 2026-05-29

**【信頼性レベル凡例】**:
- 🔵 **青信号**: 要件定義・コード調査・ユーザヒアリングで明確に必要と判明したタスク
- 🟡 **黄信号**: 要件定義から妥当に推測されるタスク
- 🔴 **赤信号**: 推測による予防的タスク

> 本要件は内部リファクタリングのため、外部 API キー・SaaS 契約・DNS 等の準備は不要。準備タスクは**メモリ削減効果を定量検証するための計測基盤**に集中する。

## 必須（実装開始前に完了が必要）

- [ ] **代表ベンチマークデータセットの用意** 🔵 *NFR-004 / ヒアリングQ4*
  - 100k trials × 約22列（パラメータ＋目的＋user attr）規模の Optuna Journal ログファイルを1つ用意する。
  - 既存の大規模 study ログがあればそれを流用、なければ Optuna で生成（多目的・パラメータ多数の study を10万試行回す等）。
  - ベースライン測定と改修後測定で**同一ファイル**を使うため、固定パスに保存しておく。
  - 関連要件: NFR-001, NFR-004, REQ-001

## 推奨（実装中に用意できればOK）

- [ ] **ベースライン（改修前）メモリ測定値の記録** 🔵 *NFR-001〜003*
  - 現行 `main` で代表データセットを読み込み、定常メモリ・ロード時ピーク・分析実行時ピークを測定して記録する。
  - 改修後の比較基準（-50% 等）の分母になるため、改修着手前に取得しておくのが望ましい。
  - 必要になるフェーズ: Phase 1 着手前
  - 関連要件: NFR-001, NFR-002, NFR-003

## 確認事項（判断が必要）

- [ ] **Windows 環境でのメモリ測定手段の確定** 🟡 *NFR-004 / 環境（win32）*
  - 候補: タスクマネージャ/リソースモニタの RSS、`dhat`（ヒーププロファイラ・`cargo bench -p tunny-core` と組み合わせ）、`heaptrack`（Linux 主体）等。
  - 定常 RSS とヒープ割当のどちらを主指標にするか、再現性のある測定手順を決める必要がある。
  - 判断の影響範囲: 受け入れ基準 TC-NFR-001/002/003 の合否判定方法。
  - 関連要件: NFR-001〜004

- [ ] **MEM-001 共有ストアのライブ更新同期方式** 🟡 *REQ-003 / EDGE-102*
  - `Arc` 共有ストア化後、ライブ更新（試行追加）時の書き込みをどう同期するか（`Arc<RwLock<_>>` / `arc-swap` で丸ごと差し替え 等）は設計フェーズ（`/tsumiki:kairo-design`）で詳細化する。
  - 本確認は要件段階では「方針＝共有ストア化」までで、具体方式は設計で決定する旨の合意確認。
  - 関連要件: REQ-002, REQ-003, EDGE-102
