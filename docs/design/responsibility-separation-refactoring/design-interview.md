# 責務分離リファクタリング 設計ヒアリング記録

**作成日**: 2026-04-15
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング

## ヒアリング目的

egui-app クレートのコード保守性向上のため、責務の分離の観点からリファクタリングの方針を確認するヒアリングを実施しました。

## 質問と回答

### Q1: リファクタリングの対象範囲

**質問日時**: 2026-04-15
**カテゴリ**: アーキテクチャ
**背景**: egui-app 全体と rust_core 両方に責務分離の課題が存在する。lib.rs の WASM バインディング分離も課題だが、ユーザーの要求が「コードの保守性」であったため範囲確認が必要。

**回答**: egui-app 全体

**信頼性への影響**:
- 設計範囲が egui-app に確定し、rust_core/lib.rs の WASM バインディング分離はスコープ外となった
- 設計の信頼性レベルは 🔵 に向上（範囲が明確）

---

### Q2: リファクタリングの移行方針

**質問日時**: 2026-04-15
**カテゴリ**: アーキテクチャ
**背景**: 大規模なリファクタリングでは一括移行と段階的移行でリスクが大きく異なる。段階的アプローチは各フェーズでテストが通ることを保証できるが、一括アプローチは中間状態の設計負債を避けられる。

**回答**: 段階的リファクタリング

**信頼性への影響**:
- 各フェーズで `cargo test` を確認するテスト戦略が確定
- フェーズ間の依存関係設計が 🔵 に向上

---

### Q3: app_state.rs の型定義とフィルタリングロジックの分離方針

**質問日時**: 2026-04-15
**カテゴリ**: データモデル
**背景**: app_state.rs (648行) がデータモデル・フィルタリングロジック・分析結果・キャッシュの4つの関心事を持つ。ファイル内のセクション整理のみでも可読性は改善するが、ファイル分割の方が責務境界が明確になる。

**回答**: 型を別ファイルに分離（types.rs / filter.rs / results.rs）

**信頼性への影響**:
- ファイル分割アプローチが確定し、モジュール構成の信頼性レベルが 🔵 に向上
- `pub use` 再エクスポートにより外部への影響を最小化できることが確認

---

### Q4: grid_canvas.rs のチャートディスパッチ分離方式

**質問日時**: 2026-04-15
**カテゴリ**: 技術選択
**背景**: show_chart() 関数が grid_canvas.rs 内にあり、グリッド描画とチャート選択の2つの関心事が混在している。分離方式としてレジストリパターン、Widget trait 統一、関数外出しの3案を提示。

**回答**: レジストリパターン（chart_registry.rs 抽出）

**信頼性への影響**:
- chart_registry.rs の設計が確定し 🔵 に向上
- 将来的なチャート追加時の変更箇所が明確になる

---

### Q5: app.rs のメッセージ処理分離方式

**質問日時**: 2026-04-15
**カテゴリ**: アーキテクチャ
**背景**: poll_messages() が AppState と WidgetStates の両方を直接変更しており、メッセージの影響範囲が app.rs に集中している。各 State に handle メソッドを追加する案と MessageHandler 構造体に集約する案を提示。

**回答**: MessageHandler 構造体抽出

**信頼性への影響**:
- MessageHandler の設計が確定し 🔵 に向上
- メッセージ処理のテストが独立して可能になる

---

### Q6: 優先フェーズの選択

**質問日時**: 2026-04-15
**カテゴリ**: 優先順位
**背景**: 3つのフェーズ（型・フィルター分離、チャートディスパッチ分離、メッセージ処理分離）に依存関係はなく、どの順序でも実施可能。ユーザーの優先順位を確認。

**回答**: Phase 1 → Phase 2 → Phase 3（全フェーズ実施）

**信頼性への影響**:
- 実装順序が確定し 🔵 に向上
- Phase 1（app_state.rs 分離）が最も影響範囲が大きいため、Phase 1 優先は妥当

---

## ヒアリング結果サマリー

### 確認できた事項
- リファクタリング対象は egui-app 全体（rust_core はスコープ外）
- 段階的リファクタリングで各フェーズ毎にテストグリーンを維持
- app_state.rs は types.rs / filter.rs / results.rs に3分割
- チャートディスパッチは chart_registry.rs にレジストリパターンで抽出
- メッセージ処理は MessageHandler 構造体に抽出
- 全3フェーズを Phase 1 → Phase 2 → Phase 3 の順で実施

### 設計方針の決定事項
- `pub use` による再エクスポートで外部モジュールへの影響を最小化
- 新規ファイル作成は最小限（types.rs, filter.rs, results.rs, chart_registry.rs, message_handler.rs の5ファイル）
- 既存テストは移動のみで内容変更なし

### 残課題
- 各フェーズの詳細なコミット分割戦略（実装時に決定）
- Widget trait の導入によるチャートウィジェットの統一（将来的な改善として保留）
