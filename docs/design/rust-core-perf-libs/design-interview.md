# rust_core 外部ライブラリ高速化 設計ヒアリング記録

**作成日**: 2026-05-15
**ヒアリング実施**: step4 設計ヒアリング

## ヒアリング目的

技術設計の観点から、外部ライブラリ導入に伴う依存関係戦略と移行順序を確認しました。

## 質問と回答

### Q1: ndarray 依存の許容

**質問日時**: 2026-05-15
**カテゴリ**: 技術選択
**背景**: linfa-clustering は ndarray ベースであり、faer::Mat ↔ ndarray::Array2 の境界変換が必要。ndarray が推移依存として追加されることでコンパイル時間とバイナリサイズに影響する。

**回答**: ndarray 許容（推奨）を選択。境界変換は受け入れる。

**信頼性への影響**:
- faer ↔ ndarray 境界変換レイヤーの設計が確定（🔵）
- K-meas の計算量に対して変換コストは無視できる（🟡）

---

### Q2: 移行順序

**質問日時**: 2026-05-15
**カテゴリ**: アーキテクチャ
**背景**: 5 つの変更領域（デッドコード、rand、faer、argmin、linfa）があり、依存関係を考慮した最適な実装順序の確認が必要。

**回答**: ボトムアップ（推奨）を選択。基盤（デッドコード削除 + rand）→ faer → argmin → linfa の順。

**信頼性への影響**:
- 5 フェーズの移行計画が確定（🔵）
- 各フェーズは独立してコンパイル・テスト可能

---

## ヒアリング結果サマリー

### 確認できた事項
- ndarray 依存は許容される
- faer ↔ ndarray 境界変換は設計に組み込む
- ボトムアップ移行（基盤→計算→外部 crate）で進める

### 設計方針の決定事項
- argmin-math は `vec` バックエンド（faer バージョン競合回避）
- linfa-clustering 導入に伴い ndarray を明示的依存に追加
- faer::Mat ↔ ndarray::Array2 変換ユーティリティを共通モジュールに配置

### 残課題
- なし（全設計方針が確定）
